## 4. 失敗の根本原因：批判的再評価

### 4A. 成果評価の歪み
多数の工程で「TECH PASS」「頂点数増」「変更画素増」「新しい真Blender完成」を進捗として数えたが、**美術・遊びは一貫してREJECT**。テストが正しくても目標を表していない（測りやすいものを改善していた）。変更したピクセル数・建築の巨大さ・CRC成功は面白さと無相関とは言えないが、少なくとも合格の根拠にはならない。

### 4B. ボトルネックと手法の不一致
SOURCE Road5/CHASE固定と画面保護により道路前景は元の大きな直線のまま。周辺の岩・フェリー・トラス・潮汐面・大屋根を順に追加しても、走行時に一番見る部分はほぼ変わらない。**背景の制作改善だけで「実コースがつまらない」を解こうとしたことが構造的な誤り**。もっと多くの岩・橋の試作は解決策ではない。

### 4C. 世界の意味・視認性不足
左の三角岩盤→灰色の滑らかな面、右の巨大模型港→別の模型港、画面から隠れる水面、上端で切れる大橋、機能と動線が読めない施設などを繰り返した。実寸・実接続・真可編集性は必要条件でも、元CHASEで「港だ」「海だ」「危険な道だ」と即座に分からなければ作品の演出としては失敗。

### 4D. 静止画・真正ゲームの混同リスク
Blender元Cameraの静止画が正しくても、ゲーム本体に統合された本物のWebGL2、連続走行、操作に対する危険/選択、車速感、fps、SAT/CCD、主観の面白さは不明。静止CHASE画像を何十枚増やしてもその欠落は埋まらない。

### 4E. 長すぎる研究とユーザー負担
K4系を細かく刻み、毎回ワークフロー追加/実Artifact 100MB超取得/監査JSON/START_HERE更新/「次へ」を繰り返した。安全ではあったが、ゲーム完成への効果が薄い工程が多かった。元の長期方針は**ユーザー作業を最小化して少数集中**であり、この運用は改善必須。

### 4F. 変更可能領域を狭く解釈しすぎた
「元Road5の変更禁止」は**原本・本番を保護すること**であり、**独立したPRIVATE研究コピーを作って実コース候補を調べることまで一律禁止ではない**。凍結原本を保持して新候補を別の識別子・研究枝で制作することは可能。ただしその候補は**元Road5の同一性を主張できない**。旧SOURCE SHAは元原本の保護に使い、候補自身には独立した新ハッシュ・独立ゲートを設ける。正式適用・PR merge・公開は承認まで絶対禁止。この区別を次期戦略の要点とする。

- **反論：Road5の研究コピーまで変えると方針がぶれるのでは？** → 本番・Gold・公式SOURCEを一切触らず、実験候補を識別し、正規240Hz/Cameraとの互換を別検証すれば方針は変わらない。コピーであることを常時明示し、原本のSHAで候補を「元Road5」と偽らない。承認なしの統合は禁止。
- **反論：1個の巨大変更では故障しやすいのでは？** → 全長を一気に改造しない。**1本の意味ある走行シーンを統合縦スライスとして制作し、その内部では実装→テスト→修正→画像/走行チェックをまとめて処理**。変更は大きな作品効果を狙うが範囲は狭くし、失敗時は研究候補だけ廃棄できる。
- **反論：人間プレイゲートはユーザー操作を増やすのでは？** → 自動/真正Chromiumと動画/スクショの証拠は作れる限りアシスタント側で用意する。人間固有の感覚・操作判断を自動QAで偽るのは不可。**最後に本当に必要な時だけ、原則一括の1クリック試走＋短い主観報告1回**にまとめる。未実施ならHUMAN HOLDのまま。

- **反論：さらに工程が増えるのでは？** → 新しい小QA/文書/候補を無制限に増やすのは停止。後述の1本のバッチで技術安全・体験・ARTをまとめ、前回の合格証拠は再利用し、失敗原因が同じなら同種トライを中止する。

**最終判断：安全ロックと完成目標はそのまま維持。制作と評価の単位だけを、景観小物から「実ゲームの一場面」へ変更。これは既存の統合縦スライス方針へ回帰する修正。**

2. **同時に目標を増やさない**：各バッチの主要目標は「一つの実プレイシーンの大きな改善」。重要でないアート家具・小物・無関係機能・大量の試作ワークフローは中止。
3. **作者コードも検証も自動化**：既存の安全なCI、監査JSON、実スクリーンショット/動画、Blender原本とArtifacts、SHA検査を再利用。失敗時は安全研究内で原因→一括修正→一括再検証を試みる。旧結果の成功を使い回して新結果と誤認しない。
4. **不要な約127MB ZIP再取得を毎回繰り返さない**：元の独立検証済みArtifactの親SHAを使う。新しい本質的候補の節目では新実ZIP全CRC/個別SHAを行うが、1行の文書更新ごとには再ダウンロードしない。
5. **START_HEREの先頭を常に単一正本への短いリンクにする**：長い追記を永久に増やすのでなく、完成済み正本と最新状態へのリンクで引継ぎ。古い「最新」は履歴と明記し、何度も全文貼付け/手動ログ転記をユーザーに要求しない。
6. **レビューは成果単位**：モデルが明確な実画面・実プレイ改善を実証できなければ「進捗あり」と言わずHOLD/REJECT。新規コミット数、CI回数、頂点数を主要KPIにしない。
7. **ユーザー操作は通常0回**。本当に必要な時だけ、ユーザーへ「1クリック起動」＋「一度だけ短い所感」の一括依頼。スクショ連投や段階的な細かい操作は避ける。ユーザーのWindowsローカル/Workが不可欠な作業は根拠と必要性を明示し、**個別承認前に開始しない**。
8. **最低限の報告形式**：何を変えたか／真の技術的根拠／ART・PLAYの現実的な判定／まだ不明なこと／保護状態／ユーザー操作が必要か、のみ。大量のQA項目は添付の機械可読ファイルに残す。
9. **無限の背景再作成を止める**：同じ原因のART REJECTが続いたら岩材・橋材・色を小刻みに増やさない。問題のクラスを「ロード形状・体験設計・カメラ視線・世界構成」のどれかに戻して仮説を更新する。
10. **既存の開発資産を捨てない**：Gold、研究歴史、K4CM–CPの真編集可能3Dと監査、既存B48/B51-C、旧成功QAは復元可能に保つ。ただしREJECT資産を正式作品へ無条件に昇格させない。

## 8. 成功／失敗と「次へ進む」の停止原則

- 本物の元Game・物理・Camera/研究親の変更を検出 → **即STOP、研究内で隔離/差分修正**。
- 同時に複数の候補を作って完成品を見失う → 1シーンの判断が終わるまで増やさない。
- Blender TECH PASS でもART REJECT → 公式採用0／PLAY HOLD。次は同じ模型調整を繰り返さず、違う原因仮説に基づく統合場面を検討。
- ブラウザ・真物理が未起動／実ゲームが未統合 → **PLAY「わからない」／HOLD**。実機に相当する確認前に「遊べる」「完成」と宣言しない。
- 既存ゲートを通すために元Road/Cameraを偽装する、閾値を勝手に緩める → 禁止。
- 将来、候補ロードを意図的に再形状化した場合は「元のRoad5画面0px差」のゲートを候補に誤適用しない。**元原本のハッシュ不変**を必須、候補形状の安全/連続走行と正規カメラ視界は別独立ゲート。既存の元Road5固定の非衝突アート工程に対する画面保護ゲート（中央120px未満・固定5点10階調等）を無断変更しない。
- 実人間プレイが求められる時点では、そのテストだけはユーザーの判断が不可欠。それ以外は可能な限り全自動。
